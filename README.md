## 티켓 발급 동시성 제어 및 비동기 처리

초과 발급 문제를 재현하고 비관적 락,비동기 메시지 처리 읽기,쓰기 분리를 단계적으로 구현
이후 RabbitMQ로 요청 접수와 발급 처리를 분리하고 MYSQL 복제와 읽기,쓰기 분리.

`2026.10` | 개인 프로젝트 

### 프로젝트 범위

- 동시 발급 시 초과 발급 및 재고 불일치 재현
- 비관적 락을 이용한 동일 티켓의 동시 변경 제어
- RabbitMQ를 이용한 비동기발급
- MYSQL A->B 복제 및 트랜잭션 기반 읽기,쓰기 연결 분리

### 발급 흐름
발급 API가 티켓 ID와 사용자 ID를 RabbitMQ에 전달하면 Consumer가 발급 서비스를 호출합니다.
발급 서비스는 MySQL A에서 대상 티켓을 잠금 조회한 뒤 재고를 차감하고 발급 내역을 저장합니다. 두 작업은 하나의 트랜잭션으로 처리합니다.

### 조회 흐름
티켓 조회는 읽기 전용 트랜잭션을 통해 MySQL B를 사용합니다. 발급 과정에 필요한 조회는 재고 변경과 함께 MySQL A에서 수행합니다.
A의 변경 내용은 B로 비동기 복제됩니다. 

### 단계별 구현
**1.동시 발급 문제 재현**

동시성 제어 없이 여러 요청이 같은 티켓의 재고를 변경하도록 요청을 보냈습니다.
여러 트랜잭션이 동일한 재고를 조회하고 변경하면서 갱신 내용을 덮어 씌우게 되면서, 초과 발급 현상과 재고 불일치가 발생하는 것을 확인했습니다.

**2.비관적 락 적용**

이전 단계에 발생 하였던 문제를 해결 하고자 발급 대상을 조회하는 단계에서 비관적 락을 적용 하였습니다.
재고 차감과 발급 내역 저장을 동일한 트랜잭션 내에서 처리하였습니다.

**3.RabbitMQ 기반 비동기 발급**

요청을 받은 시점에 발급을 직접 수행하던 흐름을 메시지 발행과 Consumer 처리로 분리했습니다.
HTTP 접수 결과와 실제 발급 결과를 구분하고 Consumer 처리 후 DB의 재고와 발급 내역을 확인했습니다.

**4.MySQL 복제 및 읽기 쓰기 분리**


읽기와 쓰기 각 목적에 따라 DB를 나누었습니다. 
쓰기의 경우 A, 읽기 전용은 B를 사용하도록 설정 하였습니다.

### 구현 및 검증

**비동기 발급:** RabbitMQ로  요청 접수와 발급 처리를 분리하고, 접수 응답과 DB의 발급 결과를 구분하여 확인하였습니다.

**읽기,쓰기 분리:** MySQL 복제와 읽기와 쓰기를 구분하여 읽기용 DB와 생성,발급용 DB로 분리하였습니다.

### 문제해결

**동시 발급으로 인한 재고 불일치**

**문제:** 재고 100장에 동시 발급 요청을 보낸 경우 초과 발급과 재고 불일치가 발생했습니다. 여러 트랜잭션이 동일한 재고를 조회한 뒤 변경하면서 갱신 내용이 덮어 써지는 현상을 확인했습니다.

**해결:** 티켓 발급  대상 조회에 비관적 락을 적용하여 티켓의 동시 변경을 제어 하였고, 재고 차감과 발급 내역 저장을 하나로 트랜잭션으로 처리하였습니다.

**결과**:  재고 100장에 1000건의 동시 발급  요청을 보내는 테스트에서 발급 내역 100건과 잔여 재고 0장을 확인했습니다.
